## 2. Data flow, single-shot vs reviewable

**Verdict: both exist.** The `mode: "single"` chain is exactly the one-shot,
unreviewable pipeline described in `docs/06`. A second chain, `mode: "override"`,
exists alongside it and is the review path. A human can review and override a
hypothesis before it is used for scoring, but only by taking that second path
deliberately — the first pass always completes unreviewed.

### Chain A — first pass, unreviewable (`mode: "single"`)

| Step | File / line |
|---|---|
| `runSingle()` declared | `app/page.tsx:1565` |
| Clears prior review state (`setApproved(null); setOverrides({}); setAppliedOverrides({})`) | `app/page.tsx:1569` |
| Issues `post({ mode: "single", text, ... })` | `app/page.tsx:1572` |
| `post()` — `fetch("/api/score", { method: "POST" })` | `app/page.tsx:1538` |
| `run()` resolves mode | `api/score.py:524-526` |
| Falls past the `override` and `batch` branches | `api/score.py:528`, `531` |
| `analyse(text, bank, corrector, ...)` — deterministic engine | `api/score.py:566` |
| `intent_layer.enrich([(text, res)], bank, corrector)` | `api/score.py:567` |
| — `enrich()` calls `flag()` to pick candidate tokens | `api/_intent/layer.py:678`, `flag()` at `132` |
| — `enrich()` calls the model via `client.fan_out`, then `_apply()` | `api/_intent/layer.py:593` |
| — `_apply()` validates verdicts through `review.validate()` and writes `corrected_sample`, `spelling_score`, `vocabulary_score` into the result | `api/_intent/layer.py:593-641` |
| `detail(res)` shapes the payload | `api/score.py:568` |
| Communicative Effect call | `api/score.py:571-583` |
| Response returned | `api/score.py:585` |
| `setSingle(data.result)` | `app/page.tsx:1578` |
| `setScreen("translate")` | `app/page.tsx:1579` |

Between `analyse()` at `score.py:566` and the scored result at `score.py:585`
there is **no human checkpoint**. The model's verdicts are validated
mechanically (`review.validate()`'s `form_test`, known-word check) but never
shown to a person before `vocabulary_score` and `spelling_score` are computed
from them. `setSingle()` receives a result that is already fully scored.

### Chain B — review and re-score (`mode: "override"`)

| Step | File / line |
|---|---|
| Review UI: Vocabulary review table with per-row controls | `app/page.tsx:1045-1193` (section 6 of `TranslateScreen`) |
| Marker's answers held in `overrides` state | `app/page.tsx:1501`, shape `Record<string, {answer, proposed?}>` |
| `rescore()` declared | `app/page.tsx:1587` |
| Issues `post({ mode: "override", baseline: single.intent_audit, overrides, ... })` | `app/page.tsx:1592` |
| `run()` dispatches to `rescore_with_overrides()` | `api/score.py:528` |
| `rescore_with_overrides()` declared | `api/score.py:449` |
| Re-runs `analyse()` on a fresh result | `api/score.py` (inside 449-522) |
| Reproduces the candidate list with `intent_layer.flag()` | `api/score.py:480` |
| Builds a synthetic verdict set from marker answers + round-tripped baseline | `api/score.py:453-478` |
| Drives `intent_layer._apply(result, items, {"verdicts": verdicts}, ...)` | `api/score.py:499` |
| Result stored separately in `approved` | `app/page.tsx:1606` |

No network call is made on Chain B — `raw` is manufactured locally, so no model
is asked. The marker's answers pass through the same `review.validate()` gates
as the model's.

### Which result downstream screens read

`Page` holds `single` (first pass) and `approved` (override-adjusted) and derives
`current = approved ?? single`. Both `TranslateScreen` and `DimensionsScreen`
receive `current`, not `single`. `DimensionsScreen` renders two banners stating
which reading produced the numbers and whether unapplied corrections exist.

### Contradiction with docs/06

`docs/06`'s item 3 ("No approve/override mechanism exists yet... everything
downstream just trusts the API's first-pass output unconditionally") does not
match the current files; `rescore_with_overrides()` at `api/score.py:449` and the
review controls at `app/page.tsx:1045-1193` both exist. As with item 2, `docs/06`
retains that text as historical record and its status update says so.

declared at `api/score.py:607`) which is the module's HTTP entry point under
Vercel's Python runtime. It was served unmodified on
`127.0.0.1:8000` via `http.server.HTTPServer(("127.0.0.1", 8000), handler)`. This
exercises the real `do_GET`, `do_POST`, JSON serialisation and headers — the same
code Vercel invokes — without `vercel dev` in the path. No project file was
touched; the launcher lives in a scratch directory.
