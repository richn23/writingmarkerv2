## 1. Investigation — do Vocabulary review overrides reach the Dimensions score?

### Short answer

**Yes — but only after the marker explicitly clicks "Re-score with my
corrections".** Changing a dropdown on the Translate screen does not move any
number by itself. Once re-scored, every figure on Dimensions is recomputed from
the marker-adjusted interpretation, and the screen says so.

So the design decision raised in the brief — re-run on every override, debounce
it, or require an explicit recalculate step — has in fact already been made, and
the answer currently in the code is **explicit recalculate**. That is worth
knowing before deciding whether to keep it.

### The state flow, in order

| # | What happens | File / line |
|---|---|---|
| 1 | Marker changes a dropdown in the Vocabulary review table | `app/page.tsx:1045-1193` |
| 2 | The change writes into `overrides`, a `Record<token, {answer, proposed?}>` | `app/page.tsx:1501` |
| 3 | Nothing else fires. `overrides` is not read by any scoring path until step 5 | — |
| 4 | `overridesDirty` flips true (`JSON.stringify(overrides) !== JSON.stringify(appliedOverrides)`) | `app/page.tsx:1509` |
| 5 | Marker clicks "Re-score with my corrections" → `rescore()` | `app/page.tsx:1587` |
| 6 | POST `mode: "override"`, sending `overrides` plus `baseline: single.intent_audit` (always the FIRST pass, never a previous override) | `app/page.tsx:1591-1602` |
| 7 | `rescore_with_overrides()` re-runs `analyse()`, reproduces the candidate list with `flag()`, builds a synthetic verdict set, drives `_apply()`. No model call | `api/score.py:449`, `480`, `499` |
| 8 | Response stored in `approved` — a *separate* state slot from `single` | `app/page.tsx:1606` |
| 9 | `appliedOverrides` is set to the overrides just applied, clearing the dirty flag | `app/page.tsx:1611` |
| 10 | `const current = approved ?? single` | `app/page.tsx:1508` |
| 11 | `DimensionsScreen` receives `current`, not `single` | `app/page.tsx:1921` |
| 12 | `DetailView` renders from that same object | `app/page.tsx:1311` |

The key line is **1508**. `approved ?? single` is what makes an override reach
Dimensions at all; without it, step 8 would write to a state slot nothing reads.
`TranslateScreen` gets `current` too (line 1909), which is why the "Intended
reading" panel also updates.

### What you actually see, right now

Verified live in the running app against the real `api/score.py` handler, using
the default sample and overriding `bote` from the model's `boat` to `It's a
name`:

| | Vocabulary | Spelling | Confident | Reported | Credible words |
|---|---|---|---|---|---|
| First pass | **42** | **96** | B1 42 | B1 49 | 30 |
| Override set, *not* re-scored | 42 | 96 | B1 42 | B1 49 | 30 |
| After clicking re-score | **47** | **98** | B1 47 | B1 48 | 29 |

Spelling rises because a proper noun is no longer counted as an error.
Vocabulary rises and credible words falls by one because `boat` is no longer
contributing to the percentile. Both are the engine doing its normal job on a
changed interpretation — nothing special-cased.

The banner text tracks it exactly:

- Before any override — *"Scored from the first-pass interpretation. No marker
  corrections have been applied…"*
- Override set, not yet applied — the same banner, **plus** a second one: *"These
  numbers do not include your latest corrections. There are unapplied changes in
  the Vocabulary review on the Translate screen — re-score there to bring them
  through."*
- After re-scoring — *"Scored from your approved interpretation. Every number
  below was recomputed after you corrected bote on the Translate screen."*

So the stale window between step 2 and step 5 is real, but it is signposted on
the screen showing the stale numbers, not left silent.

### If you want to change the trigger

Not built, not proposed — just the cost of each option, since the question was
raised:

- **Keep explicit recalculate (current).** Zero work. The marker controls when
  the number moves, and the stale state is already flagged. Costs one click.
- **Re-run on every override change.** Small change: call `rescore()` from the
  `setOverrides` handler. The backend path already makes no model call, so it is
  cheap — one `analyse()` + `flag()` + `_apply()` per keystroke. The real problem
  is the free-text "a different word" field: it would fire a re-score on every
  character typed, most of them against half-typed words that fail the form test,
  so the marker would watch their correction be rejected and re-accepted as they
  type. Would need the text field excluded or handled separately.
- **Debounce.** Same change plus a timer, roughly 400-600 ms. Removes the
  keystroke problem but introduces a window where the number on screen is
  mid-flight, which is the thing the two banners currently exist to prevent
  being invisible. Would want a visible "recalculating" state.

The load-bearing consideration is that the current design makes "the number you
are looking at" and "the corrections you have entered" two separately visible
facts. Any automatic trigger collapses them into one, which is nicer when it
works and harder to reason about when a correction is rejected.

## 3. Fix — Translate word count reads the engine's token count

`app/page.tsx`, the `stats` memo in `TranslateScreen`. Was
`trimmed.split(/\s+/).length`; now `single?.words ?? splitWords`, where
`result.words` is `totals.original.tokens` straight from `analyse()` — the same
number `DetailView` puts in its "Words" tile.

Two details worth knowing:

- **Average sentence length now derives from the same number.** It is
  `words / sentences`, so leaving it on the old whitespace count would have made
  the tile and the ratio quote different totals — a new inconsistency in place of
  the one being removed.
- **The whitespace split survives as a fallback.** With no sample scored,
  Translate shows a worked example that has never been through `analyse()`, so
  there is no engine count to read. The caption under the block says which of the
  two is on screen.

Verified live: still 71 for the default sample, now sourced from the engine.
